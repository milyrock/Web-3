# developer.dev · упрощённая лабораторная № 3

Фронтенд из второй лабораторной и backend на Go с PostgreSQL. Всё запускается одним Docker Compose.

## Запуск

Нужен запущенный Docker Desktop:

```bash
cd /Users/geprokhorov/web-3
docker compose up --build -d --wait
```

Открыть http://localhost:8080. Команда запускает Go-сервер и PostgreSQL. Go одновременно отдаёт HTML/CSS/JS и обрабатывает API. После изменений в коде повторите эту команду.

```bash
docker compose logs -f app
docker compose down
```

База сохраняется в Docker volume при остановке.

### Регистрация и вход

Пункт `Account` в бургер-меню ведёт на `/account.html`. Гость видит форму входа и ссылку на регистрацию. После входа открываются данные пользователя, корзина и кнопка покупки.

Регистрация требует имя, email, пароль от 8 до 128 символов и повтор пароля. Вход выполняется по email и паролю, без OTP. После регистрации пользователь сразу попадает в личный кабинет. Новые аккаунты всегда получают роль `user`.

Пароли хэшируются стандартным `crypto/pbkdf2`: PBKDF2-HMAC-SHA256, 600000 итераций и индивидуальная случайная соль. Сессия хранится в PostgreSQL семь дней. В HttpOnly cookie `developer_session` передаётся случайный токен, в БД хранится только его SHA-256 хэш. Выход отзывает текущую сессию. Cookie имеет `SameSite=Lax`, при HTTPS также `Secure`. Изменяющие запросы защищены `http.CrossOriginProtection`.

Для создания администратора задайте в локальном `.env`:

```dotenv
ADMIN_EMAIL=admin@developer.local
ADMIN_PASSWORD=ваш-пароль-минимум-8-символов
```

При первом запуске можно скопировать `.env.example` в `.env` и заполнить пароль. Затем выполните `docker compose up --build -d --wait`. Администратор входит через ту же форму и переходит к заявкам из личного кабинета. Пароль администратора не сохраняется в Git. Уже существующий аккаунт и его пароль при перезапуске не меняются. Без `ADMIN_PASSWORD` создание администратора пропускается.

Восстановление пароля, отправка email, OTP и управление пользователями не добавлены. Приложение рассчитано на локальное учебное использование. Перед публичным размещением нужны HTTPS, ограничение частоты входа и регистрации и проверка требований к обработке персональных данных.

### Каталог

При первом запуске в БД добавляются шесть демонстрационных услуг. Поиск работает по названию и описаниям, включая кириллицу. Есть фильтр по категории и сортировка по цене, названию и новизне. Услуги с выключенным флагом доступности скрываются из каталога. Остаток показан в каталоге и карточке. При нулевом остатке кнопка добавления отключена.

### Обратная связь

Поля: имя, email, тема, сообщение, необязательная оценка 1–5 и согласие на обработку данных. Данные проверяются в браузере и на сервере, затем сохраняются в PostgreSQL. Отправка email не подключена.

Администратор просматривает заявки на `/admin.html`. Также их можно посмотреть напрямую в базе:

```bash
docker compose exec db psql -U developer -d developer -c 'SELECT id,name,email,subject,created_at FROM feedback ORDER BY id DESC LIMIT 20'
```

### Корзина

Корзина находится в личном кабинете и доступна после входа. Добавлять услуги из каталога можно заранее, выбранные позиции сохранятся после входа или регистрации.

Хранится только в localStorage браузера. Сохраняются ID услуг и количество. Корзина общая для аккаунтов в одном браузере. Актуальные названия, цены и остатки загружаются из БД. Можно изменить количество, удалить позицию и очистить корзину. Удалённые или скрытые услуги убираются из корзины при загрузке.

Количество одной услуги ограничено диапазоном от 1 до 10. Сохранённые ранее значения выше 10 уменьшаются до нового лимита при загрузке корзины.

### Покупка

Кнопка «Купить» отправляет позиции на `POST /api/purchase`. Покупать могут только вошедшие пользователи, включая администратора. В `products.stock` хранится целочисленный остаток. При миграции существующим услугам назначается по 10 единиц, последующие перезапуски остатки не меняют.

Репозиторий списывает все позиции в одной SQL-транзакции. Условный `UPDATE` проверяет доступность и достаточный остаток. Если хотя бы одной услуги не хватает, вся транзакция откатывается и API возвращает `409`. Одновременные покупки не могут увести остаток в минус. Позиции обрабатываются в порядке ID, чтобы параллельные корзины блокировали строки в одном порядке.

После успеха корзина очищается и появляется сообщение «Успех! Покупка выполнена». При нехватке остатка корзина сохраняется, её данные обновляются. Реальная оплата, история покупок и таблицы заказов не добавлены.

**Это локальная учебная версия.** Docker публикует порты только на `127.0.0.1`. Используйте тестовые данные.

## Что убрано

- Управление пользователями.
- Журнал действий и история поиска в сессии.
- Серверная корзина, реальная оплата и история заказов.
- Добавленный слайдер на главной. Исходный первый блок второй лабораторной восстановлен.
- Редактирование услуг и модерация заявок. Администратору доступен только просмотр обращений.
- Отдельные ручки поиска и проверки состояния. Поиск работает через параметры каталога, Docker проверяет доступность главной страницы.

Поэтому текущая версия выполняет только часть исходного задания. Привязка корзины к пользователю, заказы, CRUD услуг и слайдер отсутствуют.

## Три слоя backend

```text
HTTP-запрос
    ↓
handlers      читает запрос и возвращает JSON
    ↓
usecase       проверяет данные и выполняет логику
    ↓
repository    выполняет SQL-запросы
    ↓
PostgreSQL
```

Пример отправки формы: `web/script.js` делает `POST /api/feedback`. Handler читает JSON. Usecase проверяет имя, email и сообщение. Repository сохраняет обращение. Handler возвращает результат браузеру.

Структура JSON-запроса находится в `handlers/create_feedback`, структуры JSON-ответов в `handlers/response/dto.go`. Handler преобразует запрос в `model.Feedback` и отдельно передаёт согласие в usecase. Доменные модели в `model` не содержат JSON-тегов. Usecase работает с ними и интерфейсом репозитория. HTTP, JSON и SQL в usecase отсутствуют.

Слои связаны через интерфейсы:

- `usecase.Repository` в `internal/usecase/service.go` описывает методы работы с данными. `Service` принимает этот интерфейс в `New`.
- В каждой папке ручки интерфейс `Usecase` содержит только метод, который вызывает эта ручка.
- `handlers.Usecase` объединяет интерфейсы ручек для сборки маршрутов.
- Конкретные `repository.Repository` и `usecase.Service` связываются в `cmd/server/main.go`.

Запросы к данным собираются через `github.com/Masterminds/squirrel` с алиасом `sq`. Формат `sq.Dollar` автоматически формирует PostgreSQL-плейсхолдеры `$1`, `$2`. Создание таблиц и миграции выполняются обычным SQL.

Каждая API-ручка имеет свою папку и файл `handler.go`. В `router.go` находятся только подключения обработчиков и общие HTTP-заголовки.

## Все API-ручки

| Метод и адрес | Папка в `internal/handlers/` | Назначение |
|---|---|---|
| `GET /api/categories` | `list_categories` | Список категорий |
| `GET /api/products` | `list_products` | Каталог, поиск, фильтрация и сортировка |
| `GET /api/products/{id}` | `get_product` | Одна услуга со свойствами и изображениями |
| `POST /api/feedback` | `create_feedback` | Сохранение обращения |
| `GET /api/feedback` | `list_feedback` | Список обращений, только администратор |
| `POST /api/auth/register` | `register` | Регистрация и вход |
| `POST /api/auth/login` | `login` | Вход по email и паролю |
| `POST /api/auth/logout` | `logout` | Выход из текущей сессии |
| `GET /api/auth/me` | `current_user` | Данные текущего пользователя |
| `POST /api/purchase` | `purchase` | Покупка корзины и списание остатков |

Параметры каталога и поиска:

- `q` задаёт поисковый запрос.
- `category` задаёт ID категории.
- `sort`: `name`, `price_asc`, `price_desc`, `newest`.

Пример: `/api/products?q=сайт&category=1&sort=price_asc`. Каталог и карточка возвращают только доступные услуги.

Тело запросов передаётся в JSON с `Content-Type: application/json`. Пример обращения:

```json
{
  "name": "Иван",
  "email": "ivan@example.com",
  "subject": "Разработка сайта",
  "message": "Хочу обсудить новый проект.",
  "rating": 5,
  "consent": true
}
```

`rating` можно передать как `null`.

Для регистрации передаются `name`, `email`, `password` и `password_confirmation`. Для входа передаются `email` и `password`. Роль при регистрации передавать нельзя. Данные паролей и токенов не входят в JSON-ответы.

Тело запроса покупки:

```json
{
  "items": [
    {"product_id": 1, "quantity": 2},
    {"product_id": 3, "quantity": 1}
  ]
}
```

В запросе допускается от 1 до 50 разных услуг с количеством от 1 до 10. Остатки проверяет сервер в транзакции.

## База данных

В новой базе создаются восемь предметных таблиц:

1. `manufacturers` хранит исполнителя услуг.
2. `categories` хранит категории.
3. `products` хранит услуги, описания, цены, доступность и остаток `stock`.
4. `product_properties` хранит свойства услуг.
5. `product_images` хранит дополнительные изображения.
6. `feedback` хранит обращения.
7. `auth_users` хранит аккаунты, хэши паролей и роли.
8. `auth_sessions` хранит хэши токенов сессий и срок действия.

Версия схемы фиксируется в `schema_migrations`. Цены хранятся целыми рублями. Каталог связан внешними ключами. При удалении услуги её свойства и изображения удаляются каскадно.

Для существующей БД автоматически обновляется форма хранения обращений и добавляются таблицы авторизации. Каталог и старые обращения сохраняются. Исторические таблицы пользователей, сессий и заказов, если они остались от ранней версии, сохраняются отдельно. Текущая авторизация использует `auth_users` и `auth_sessions`.

```bash
docker compose exec db psql -U developer -d developer -c '\dt'
```

## Локальный запуск Go

Нужен Go 1.26+:

```bash
docker compose up -d --wait db
go run ./cmd/server
```

Используйте этот вариант вместо запуска контейнера `app`, чтобы порт 8080 был свободен.

| Переменная окружения | По умолчанию |
|---|---|
| `ADDR` | `127.0.0.1:8080` |
| `DATABASE_URL` | `postgres://developer:developer@localhost:5433/developer?sslmode=disable` |
| `WEB_DIR` | `web` |
| `ADMIN_EMAIL` | `admin@developer.local` |
| `ADMIN_PASSWORD` | Пусто. Создание администратора отключено |

Go читает переменные окружения напрямую. Для локального `go run` задайте `ADMIN_EMAIL` и `ADMIN_PASSWORD` в окружении, если нужно создать администратора. Docker Compose автоматически читает `.env`. Пример конфигурации есть в `.env.example`.

## Проверки

```bash
docker compose up -d --wait db
TEST_DATABASE_URL='postgres://developer:developer@localhost:5433/developer?sslmode=disable' go test -race ./...
go vet ./...
```

Каждый интеграционный тест создаёт свою временную схему PostgreSQL и удаляет только её. Без `TEST_DATABASE_URL` эти тесты пропускаются. Проверяются каталог, поиск, доступность услуг, сохранение обращений, регистрация, повтор пароля, вход и выход, истечение сессий, доступ администратора, покупка, откат всей корзины при нехватке остатка, одновременные покупки, валидация и HTTP-защита.
